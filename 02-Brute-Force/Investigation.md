# Brute-Force Investigation

## 1. Alert

A Splunk scheduled alert named:

**Windows Brute Force - Multiple Failed Logons**

was configured to identify three or more failed Windows logon attempts within a one-minute window.

The alert was successfully triggered during a controlled authentication test.

---

## 2. Initial Investigation

The investigation started by searching for Windows Event ID 4625:

```spl
index=wineventlog 4625
```

Event ID 4625 represents a failed Windows logon attempt.

The search was then used to inspect the frequency and timing of the failed authentication events.

---

## 3. Detection Pattern

The failed logons were grouped into one-minute windows.

The investigation identified multiple failed authentication attempts occurring within short periods.

### Verified Test Result

| Time Window | Source IP | Logon Type | Failed Logins |
| ----------- | --------- | ---------: | ------------: |
| 17:50:00    | 127.0.0.1 |          2 |             4 |

The `17:50:00` sequence represents a verified burst where four interactive failed logons occurred within approximately 10 seconds, between `17:50:20` and `17:50:30`.

---

## 4. Source Analysis

The source IP was extracted from the raw Windows event data.

Observed value:

```text
127.0.0.1
```

`127.0.0.1` is the loopback address and indicates that the authentication activity originated locally from the Windows lab machine.

The host associated with the events was:

```text
Kakarot
```

This was the analyst's Windows 11 lab system.

---

## 5. Logon Type Analysis

The observed Logon Type was:

```text
2
```

Windows Logon Type 2 represents an **Interactive logon**.

This is consistent with the controlled test because the failed authentication attempts were intentionally generated through the Windows login interface.

---

## 6. Authentication Failure Analysis

The investigation extracted the Windows authentication status fields.

Observed values:

```text
Status:    0xc000006d
SubStatus: 0xc0000380
```

These values were consistently observed across the failed authentication events generated during the lab.

The presence of Event ID 4625 together with these authentication status values confirms that the Windows authentication attempts failed.

---

## 7. Timeline Analysis

One controlled test sequence produced four failed authentication attempts within approximately ten seconds.

### Example Sequence

| Time     | Event | Description               |
| -------- | ----: | ------------------------- |
| 17:50:20 |  4625 | Failed logon              |
| 17:50:24 |  4625 | Failed logon              |
| 17:50:27 |  4625 | Failed logon              |
| 17:50:30 |  4625 | Failed logon              |
| 17:50:50 |  4624 | Successful authentication |

The successful authentication occurred approximately 20 seconds after the final failed event.

Additional controlled test sequences, including a test around `23:01`, also produced failed attempts that triggered the configured alert.

---

## 8. Successful Authentication Correlation

Successful Windows authentication events were investigated using Event ID 4624.

A successful authentication was observed after the failed authentication sequence.

Relevant observations included:

* **Event ID:** `4624`
* **Source IP:** `127.0.0.1`
* **Logon Type:** `11`
* **Authentication Package:** `Negotiate`

Logon Type 11 represents a cached interactive authentication.

Additional Logon Type 7 events were also observed during workstation unlock activity.

These events were not treated as separate suspicious incidents because they were generated as part of normal activity on the analyst's Windows lab machine.

---

## 10. Classification

**Classification: Benign / Controlled Lab Simulation**

The activity was intentionally generated by the analyst to test the Splunk detection and alerting workflow.

There is no evidence from this lab exercise that an external attacker targeted the system.

The detection should therefore be considered a **successful detection test**, rather than evidence of a real security incident.

---

## 11. MITRE ATT&CK Mapping

**T1110 — Brute Force**

The repeated authentication failures are consistent with behavior associated with the Brute Force technique.

This mapping describes the behavior that the detection is designed to identify.

It does not establish that the controlled lab activity was a real brute-force attack.

```text

     ↓

     ↓

     ↓
Review Authentication Status
     ↓

     ↓

     ↓

     ↓
Classify Activity
```

---

## 13. Recommended Analyst Actions in a Real Environment

If the same detection occurred on a production system, an analyst should investigate further before closing the alert.

Recommended actions would include:

1. Identify the source IP and determine whether it is internal or external.
2. Identify the targeted account.
3. Determine whether the source IP is known and authorized.
4. Check for additional failed authentication events.
5. Look for successful authentication following the failures.
6. Review other Windows Security events around the same time.
7. Check whether the account was locked out.
8. Investigate unusual processes or activity associated with the host.
9. Determine whether the behavior is expected or suspicious.
10. Escalate according to the organization's incident response process if malicious activity is suspected.

These actions were not required for the lab classification because the test activity was intentionally generated by the analyst.

---

## 14. Conclusion

The Splunk detection successfully identified repeated Windows authentication failures generated during a controlled lab simulation.

The investigation confirmed:

* Windows Event ID 4625 events were collected successfully.
* Multiple failures could be detected within a one-minute window.
* Relevant authentication fields could be extracted from raw event data.
* The source and host could be identified.
* Authentication failure status values could be investigated.
* Successful authentication events could be correlated with failed attempts.
* A scheduled Splunk alert successfully triggered.
* The activity could be classified correctly as a controlled lab simulation.

This project demonstrates a basic end-to-end SOC workflow from **SIEM detection to investigation and classification**.
